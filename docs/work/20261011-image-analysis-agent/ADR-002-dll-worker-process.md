## 요약

- 목적: 과제별 C DLL을 Agent에서 어떻게 호출할지, 격리 수준을 어디까지 둘지 결정한다.
- 현재 결론 또는 상태: 해커톤 P0는 메인 프로세스에서 `ctypes`로 직접 호출하고 예외·반환 코드만 처리한다. 같은 시그니처의 mock을 먼저 만든다. 별도 워커 프로세스 격리는 P2로 두되, 32비트 DLL이거나 리허설에서 크래시가 나면 앞당긴다. 승인 대기.
- 다음 행동: 설계 승인과 함께 `approved`로 전환. Q-08(시그니처·비트 수) 확정 후 어댑터 구현.

## 배경

DLL은 C 함수다(사용자 답변). 시그니처·비트 수·입력 형식은 미확인이고 해커톤 당일에야 확인될 수 있다(RISK-08). 12시간 제한(C-01) 안에 P0를 끝내야 한다. 네이티브 크래시는 Python 프로세스를 종료시키지만, 해커톤 시연에서는 MCP 서버를 다시 띄우면 된다.

## 고려한 대안

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A | 메인 프로세스에서 `ctypes.WinDLL`로 직접 호출, 예외·반환 코드 처리 | 가장 단순, 1시간 안에 구현, 오버헤드 없음 | 크래시 시 서버 종료, 행 시 타임아웃 불가, 32비트 DLL 불가 |
| B | 호출마다 별도 Python 워커 프로세스 + JSON 통신 | 크래시·행 격리, 타임아웃, 32비트 인터프리터 지정 가능 | 구현 1~2시간 추가, 임시 파일 전달, 프로세스 시작 비용 |
| C | 상주 DLL 서비스 | 반복 호출 성능 | 해커톤 범위 밖 |

## 결정

P0는 A, P2는 B.

- 어댑터는 과제당 1파일이며 설계 3.5의 `DllAdapter` 프로토콜을 구현한다. 레지스트리 `dll.kind`가 `c`면 ctypes, `mock`이면 같은 시그니처의 Python 구현을 쓴다.
- 예외와 반환 코드 ≠ 0은 `dll_status: failed`로 기록하고 파이프라인은 계속한다(AC-05).
- B로 전환하는 조건: DLL이 32비트로 확인됨, 리허설에서 크래시 발생, 호출이 10초를 넘겨 타임아웃이 필요함. 전환 시 어댑터 코드는 그대로 두고 호출 경로만 워커로 바꾼다.
- `faulthandler`를 켜서 크래시 시 스택을 `run.log`에 남긴다.

## 결과

- 장점: P0 구현 시간을 최소화한다. mock으로 DLL 없이도 전체 흐름을 시연한다(NFR-07, RISK-08).
- 감수할 단점: 시연 중 DLL 크래시가 나면 서버 재시작이 필요하다. 리허설로 사전에 확인한다.
- 영향 범위: DES-07, 설계 3.2 `dll` 절, 3.5, AC-04, AC-05, 9.2 타임라인 2:30~4:00.
