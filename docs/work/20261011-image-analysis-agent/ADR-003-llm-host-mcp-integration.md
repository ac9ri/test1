## 요약

- 목적: 사내 GLM-5.3-Flash를 어떤 경로로 Agent에 연결할지, Agent의 실행 주체를 어디에 둘지 결정한다.
- 현재 결론 또는 상태: Agent 런타임은 사내 호스트 프로그램(클로드 데스크톱 유사)이고, 우리 코드는 MCP 도구 서버와 같은 코어를 쓰는 CLI다. 호스트가 MCP를 지원하지 않으면 연동 사다리(B 로컬 명령, C 채팅 전용, D API)로 내려간다. LLM 클라이언트 코드는 쓰지 않는다. 승인 대기.
- 다음 행동: 설계 승인과 함께 `approved`로 전환. 해커톤 시작 30분 안에 호스트 확장 방식 확인(Q-07).

## 배경

사용자 답변(2026-10-11): 사내 GLM은 "클로드 데스크톱 같은 사내 프로그램"을 통해 쓴다. API 접속 정보는 없다. 해커톤 12시간 안에 사내 LLM을 쓰는 Agent를 만들어야 한다. 공개 사양상 GLM-5.3-Flash는 이미지 입력과 함수 호출을 지원하며(C-05), 클로드 데스크톱 계열 호스트는 MCP 서버를 등록해 도구를 호출한다.

## 고려한 대안

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A | 1차 초안: OpenAI 호환 API 클라이언트로 우리 코드가 LLM을 호출하는 자체 Agent | 호스트 독립, 배치 자동화 | API가 없거나 미확인이면 동작 불가. 클라이언트·재시도·구조화 출력 파싱 구현에 2~3시간 소요 |
| B | 호스트 프로그램을 Agent 런타임으로 쓰고 우리 코드는 MCP 도구 서버 | LLM 클라이언트 코드 불필요, 호스트의 도구 루프·이미지 표시·대화를 그대로 활용, 시연이 자연스러움 | 호스트가 MCP를 지원해야 함(A-06). 배치 자동화는 호스트 UI에 묶임 |
| C | 호스트가 로컬 명령 실행·파일 읽기만 지원하는 경우: CLI를 도구처럼 쓰는 지침 작성 | 코어 재사용 | 호스트가 파일을 읽어 판단하므로 결과 전달이 느슨함 |
| D | 호스트가 채팅만 지원: CLI가 해석 요청 프롬프트를 생성, 사용자가 붙여넣기 | 어떤 환경에서도 동작 | 반자동. Agent라 부르기 어려움 |

## 결정

B를 P0로 채택하고 C → D 순서를 대체 경로로 둔다. A는 API가 확인될 때 CLI에 클라이언트 한 층을 더하는 방식으로 추가할 수 있다.

- 코어(로더·기본 평가·DLL·판정·보고서)는 LLM과 호스트를 모른다(NFR-01). MCP 서버와 CLI가 코어를 감싼다.
- MCP 서버는 FastMCP(stdio)로 만들고 도구 5개(`list_inputs`, `get_chart_catalog`, `analyze_image`, `get_preview`, `write_report`)를 노출한다.
- VLM 판별·해석은 코드가 아니라 호스트 시스템 프롬프트(설계 5.3)로 구현한다. 구조화 출력·스키마 검증 코드는 쓰지 않는다. 서버는 도구 인자를 레지스트리로 검증한다.
- 호스트에는 1024px 프리뷰만 전달한다(NFR-02).
- 해커톤 시작 30분 안에 호스트 확장 방식을 확인하고, MCP가 안 되면 4:00 시점에 C 또는 D로 전환한다(설계 9.4).

## 결과

- 장점: 12시간 안에 끝낼 수 있는 가장 짧은 경로다. 사내 프로그램의 GLM을 "그 프로그램의 방식대로" 쓰므로 해커톤 취지에 맞는다. 코어는 모든 대체 경로에서 재사용된다.
- 감수할 단점: 자동 배치는 범위 밖이 된다. 호스트의 도구 루프 동작(병렬 호출, 이미지 표시)은 우리가 통제할 수 없어 프롬프트와 입력 검증으로 보완한다.
- 영향 범위: DES-08, DES-10, 설계 2.3·5절, FR-07, AC-11. 1차 초안의 `LlmClient`·`probe-llm` 설계는 제거된다.
