# ADR-001: LLM과 결정적 코드의 역할 분리

> 문서 유형: `adr`
> 작업 ID: `20261011-image-analysis-agent`
> 상태: `proposed`
> 기준선: `draft`
> 작성일: 2026-10-11
> 최종 갱신: 2026-10-11
> 관련 문서: [REQ-image-analysis-agent: 요구사항](../../requirements.md), [DESIGN-image-analysis-agent: 설계](../../design.md)

## 요약

- 목적: Agent에서 LLM(사내 호스트 프로그램의 GLM-5.3-Flash)이 맡을 일과 결정적 코드가 맡을 일의 경계, 그리고 호스트의 도구 호출 루프 안에서 실행을 어떻게 통제할지 결정한다.
- 현재 결론 또는 상태: LLM은 차트 유형 판별 보조·사용자 확인·결과 해석만 맡고, 수치 계산·판정·단계 순서는 코드가 맡는다. 호스트의 도구 루프는 피할 수 없으므로 매크로 도구 하나가 결정적 단계를 묶어 LLM 판단 지점을 최소화한다. 승인 대기.
- 다음 행동: 설계 승인과 함께 `approved`로 전환.

## 배경

사용자는 "차트 이미지에 따라 자동으로 분석할 내용을 찾아 진행"하고 "과제 차트면 DLL로 값을 계산"하기를 원한다. 수치는 재현 가능해야 하고(NFR-03) 과제 DLL이 계산 로직을 이미 갖고 있다. LLM은 사내 호스트 프로그램 안에서만 쓸 수 있고(C-02), 호스트가 도구 호출 루프를 제공한다. GLM-5.3-Flash는 thinking을 끌 수 없어 도구 호출마다 지연이 누적된다.

## 고려한 대안

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A | LLM이 프리뷰를 보고 직접 수치를 읽거나 계산한다 | 구현 최소 | 재현 불가, 환각, DLL 목적과 충돌. 거부 |
| B | 세분화 도구(load, classify, basic, dll, judge, report)를 노출하고 LLM이 매 단계 다음 도구를 고른다 | 유연, 대화형 탐색 쉬움 | 이미지당 6회 이상 호출로 thinking 지연 누적, 순서 누락 위험, 디버깅 어려움 |
| C | 매크로 도구 `analyze_image`가 로드→판별(규칙)→기본 평가→DLL→판정을 한 번에 수행하고, LLM은 unknown·needs_input 처리와 해석 문장만 맡는다. 시스템 프롬프트가 순서를 고정한다 | 이미지당 2~3회 호출, 설명 가능, LLM 없이도 CLI로 동일 수치 | 대화형 세부 질의는 별도 도구 필요 |

## 결정

C를 채택한다.

- LLM 역할: (1) 규칙 판별이 실패했을 때 프리뷰를 보고 차트 유형 선택 또는 사용자에게 질문, (2) raw 추정이 불확실할 때 사용자에게 사양 확인, (3) 판정 표를 받아 요약·해석·권고 작성, (4) 사용자와의 대화.
- 코드 역할: 로드, raw 추정, 규칙 판별, 기본 평가, DLL 호출, 임계값 판정, 단계 순서, 수치 표 렌더링, 입력 검증.
- 도구 인자(`chart_type`, `project_id`, `analysis_id`)는 서버가 레지스트리로 검증하고 오류에 허용 목록을 담아 돌려준다. LLM이 임의 분석을 실행할 수 없다.
- 보고서 수치 표는 코드가 삽입한다. LLM 문장은 표의 값만 인용하도록 프롬프트로 지시한다.
- B의 세분화 도구(`run_analysis` 등)는 대화형 질의가 필요해지면 P2로 추가한다.

## 결과

- 장점: AC-07·AC-10을 구조적으로 만족한다. 호스트 없이도 CLI로 같은 수치가 나온다(S-05). 호출 수가 적어 시연 지연이 작다(RISK-04).
- 감수할 단점: "자동으로 찾아서"의 범위가 레지스트리 카탈로그로 제한된다. 새 분석은 사람이 등록한다.
- 영향 범위: DES-02, DES-08, DES-10, 설계 4.1·5.3절, AC-07, AC-09, AC-11.
