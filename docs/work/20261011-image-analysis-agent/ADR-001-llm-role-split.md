# ADR-001: LLM과 결정적 코드의 역할 분리

> 문서 유형: `adr`
> 작업 ID: `20261011-image-analysis-agent`
> 상태: `proposed`
> 기준선: `draft`
> 작성일: 2026-10-11
> 최종 갱신: 2026-10-13
> 관련 문서: [REQ-image-analysis-agent: 요구사항](../../requirements.md), [DESIGN-image-analysis-agent: 설계](../../design.md)

## 요약

- 목적: Agent에서 LLM(사내 GLM-5.3-Flash)이 맡을 일과 결정적 코드가 맡을 일의 경계, 그리고 실행 순서를 누가 통제할지 결정한다.
- 현재 결론 또는 상태: LLM은 차트 유형 판별 보조·결과 해석·결과 질의응답만 맡고, 수치 계산·판정·단계 순서는 코드(웹 백엔드의 파이프라인)가 맡는다. 불확실한 지점은 LLM이 추측하지 않고 사용자에게 화면으로 확인한다. 승인 대기.
- 다음 행동: 설계 승인과 함께 `approved`로 전환.

## 배경

사용자는 "차트 이미지에 따라 자동으로 분석할 내용을 찾아 진행"하고 "과제 차트면 DLL로 값을 계산"하기를 원한다. 수치는 재현 가능해야 하고(NFR-03) 과제 DLL이 계산 로직을 이미 갖고 있다. Agent는 웹 앱이며 LLM은 백엔드가 API로 호출하되 API가 없을 수도 있다(C-02). GLM-5.3-Flash는 thinking을 끌 수 없어 호출마다 지연이 누적된다.

## 고려한 대안

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A | LLM이 프리뷰를 보고 직접 수치를 읽거나 계산한다 | 구현 최소 | 재현 불가, 환각, DLL 목적과 충돌. 거부 |
| B | LLM 도구 루프가 매 단계(load, classify, basic, dll, judge, report)를 결정하는 ReAct 오케스트레이션 | 유연 | 이미지당 6회 이상 호출로 지연 누적, 순서 누락, API 없으면 전체가 멈춤 |
| C | 코드가 파이프라인 순서를 고정하고 LLM은 세 판단 지점(규칙 판별 실패 시 후보 제시, 서술 작성, 결과 질의응답)에서만 호출. 불확실하면 사용자에게 확인 | 이미지당 LLM 호출 ≤ 2회, LLM 없이도 수치·판정 동일, 설명 가능 | 자동 탐색 범위가 카탈로그로 제한 |

## 결정

C를 채택한다.

- LLM 역할: (1) 규칙 판별이 실패했을 때 프리뷰로 차트 유형 후보 제시(임계값 이상이면 채택, 아니면 사용자 선택), (2) 판정 표를 받아 요약·해석·권고 작성, (3) 결과 화면 채팅에서 도구(`get_result`, `run_analysis`, `get_catalog`)를 순차 호출해 답변(P1).
- 코드 역할: 로드, raw 추정, 규칙 판별, 기본 평가, DLL 호출, 임계값 판정, 단계 순서·상태 기계, 수치 표 렌더링, 입력 검증, 확인 요청(`needs_input`).
- API와 채팅 도구의 `chart_type`·`project_id`·`analysis_id`는 레지스트리로 검증하고 오류에 허용 목록을 담는다. LLM이 임의 분석을 실행할 수 없다.
- 보고서 수치 표는 코드가 삽입한다. LLM 문장은 표의 값만 인용하도록 프롬프트로 지시하고, P1에서 문장 속 숫자를 표와 대조한다.
- LLM API가 없으면 (1)은 사용자 선택, (2)는 수동 붙여넣기, (3)은 비활성화로 대체된다.

## 결과

- 장점: AC-07·AC-10을 구조적으로 만족한다. API 없이도 CLI·웹에서 같은 수치가 나온다(S-05, S-08). 호출 수가 적어 결과 화면 지연이 작다(RISK-04).
- 감수할 단점: "자동으로 찾아서"의 범위가 레지스트리 카탈로그로 제한된다. 새 분석은 사람이 등록한다.
- 영향 범위: DES-02, DES-08, DES-12, 설계 4.1·4.2·5절, AC-07, AC-09, AC-14, AC-15.
